# 持续修改与完善流程

## 适用场景
用户对已生成的文档提出修改意见，需要持续完善。

---

## 持续修改的关键原则

### 1. 避免过度精细化
- 追问和修改补充应聚焦于**当前阶段的核心内容**
- 避免让文档过度变为明显不适合该阶段的颗粒度
- 保持文档结构与当前PRD阶段的一致性

### 2. 避免AI化撰写风格
- 在修改和补充内容时，继续保持真实自然的撰写风格（参考：见 [writing-style-guide.md](writing-style-guide.md)）
- 避免为追求"完整性"而添加过于机械化的表达
- 不要使用抽象空洞的概念堆砌（如"赋能"、"闭环"等）
- 补充内容应具有具体的业务场景和细节，而不是泛泛而谈
- 保持句式的多样性，避免每部分都使用相同的表达方式
- 允许部分内容保持简洁，不必过度扩展

### 3. 阶段一致性检查
- 每次修改前，检查修改要求是否涉及文档用途或阶段的变更
- 如果修改要求会让文档从一个阶段偏移到另一个阶段，必须提示用户

**提示示例**：
```
注意：您提出的这个修改涉及[技术实现细节]，
这会让文档从"方案成型阶段"转变为"实现阶段"。
如果继续修改，文档将更接近Technical PRD而非Systemic Solution PRD。
是否确认继续？或考虑更换为更合适的文档框架？
```

### 4. 识别阶段前进信号
- 持续的追问和修改可能表明用户需求在前进
- 如果以下模式出现，说明文档阶段在前进：
  - 从整体方案→功能细节实现
  - 从假设验证→技术实现方案
  - 从商业价值分析→具体功能定义
- 当识别到阶段前进时，需主动提示用户

### 5. 获得用户确认后再推进
- 在确认阶段变更或前进之前，先获得用户的正向反馈
- 明确说明变更的影响和后果

**对话示例**：
```
智能体：您提出的这个修改会显著增加技术实现细节，
         这会让文档更偏向Technical PRD。

         当前使用的是Systemic Solution PRD（方案成型阶段），
         它的重点是整体方案设计和系统边界，
         而Technical PRD的重点是技术实现细节和接口定义。

         两个文档框架的颗粒度和侧重点不同。

         您是想让文档前进到实现阶段吗？
         还是继续在方案成型阶段完善？

用户：我理解了，还是保持在方案成型阶段。

智能体：好的，那我们聚焦于整体方案的完善，
         技术细节可以标注为[待补充]或放到后续的Technical PRD中。
```

## 持续修改流程

当用户提出修改意见时，执行以下步骤：

### 步骤1：分析修改要求
- 识别修改的具体内容（增加、删除、调整）
- 判断修改是否涉及文档用途变更
- 判断修改是否涉及阶段偏移
- 检查用户是否提供了外部参考（文档、链接、知识库等）

### 步骤2：处理外部参考（如有）
- 如果有外部参考：
  - 按照参考资料处理流程读取、验证、提取参考内容（参考：见 [reference-processing-guide.md](reference-processing-guide.md)）
  - 将外部参考作为修改的依据
  - 在文档中标注参考来源：`[参考: 来源]`

### 步骤3：阶段一致性检查
- 如果修改涉及阶段偏移：
  - 提示用户当前文档的阶段定位
  - 说明不同阶段的文档框架差异
  - 获得用户确认
- 如果用户确认阶段前进：
  - 建议切换到新的阶段文档框架
  - 或在当前文档框架中保持当前阶段的颗粒度

### 步骤4：评估修改对结构和撰写风格的影响
- 检查修改是否会破坏文档框架结构
- 评估是否需要调整章节组织
- 识别是否超出当前阶段的颗粒度范围
- 评估修改内容是否会导致AI化撰写风格：
  - 是否过于机械化或抽象
  - 是否缺乏具体业务场景
  - 是否堆砌空洞概念

### 步骤5：执行修改并保持撰写风格
- 如果确认修改合适且不涉及阶段偏移：
  - 直接应用修改
  - 保持文档结构完整
  - 确保修改内容保持真实自然的撰写风格（参考：见 [writing-style-guide.md](writing-style-guide.md)）
  - 避免使用空洞概念和机械化表达
  - 加入具体的业务场景和细节
  - 如果基于外部参考进行修改，在文档中标注参考来源：`[参考: 来源]`
- 如果涉及阶段偏移但用户坚持：
  - 警告用户可能导致文档结构不一致
  - 在修改位置标注`[阶段偏移提醒]`
  - 建议后续切换到更合适的文档框架

### 步骤6：文档结构化补充
- 对于超出当前颗粒度的修改：
  - 标注为`[超阶段颗粒度]`
  - 给出建议：这个内容适合放在哪个阶段或哪个文档
  - 示例：`[超阶段颗粒度] 建议:此技术实现细节更适合Technical PRD或Feature PRD`

### 步骤7：撰写风格检查
- 检查修改后的内容是否出现AI化特征（参考：见 [writing-style-guide.md](writing-style-guide.md)）
- 如有，调整为更自然、具体的表达
- 确保整体文档风格保持一致

### 步骤8：全文读和去重检查
- 执行全文读和去重检查（参考：见 [final-check.md](final-check.md)）

### 步骤9：输出更新后文档
- 重新生成完整文档
- 保持格式统一
- 在文档末尾添加修改记录（如需要）

## 阶段前进的新文档创建流程

当用户确认进入下一个大阶段时：

### 步骤1：提醒保存当前阶段文档
```
智能体：在创建新文档之前，请先保存当前阶段的最终文档。
         当前文档：[模板名称]
         建议保存文件名：[建议的文件名]

         请确认您已保存当前文档。
```

### 步骤2：创建新文档
```
智能体：新文档已生成。

         文档关系：
         - 上一个阶段文档：[文件名1]（已保存）
         - 当前阶段文档：[文件名2]（新创建）

         新文档基于上一阶段的内容重新组织，
         保持了阶段的独立性和演进关系。
```

### 步骤3：明确文档关系
- 用表格清晰说明各阶段文档的关系和作用
- 参考文件命名规范：`[项目名称]_[阶段]PRD_[日期].md`

---

## 文档命名规范

### PRD阶段文档命名格式
```
[项目名称]_[阶段简称]PRD_[日期].md
```

### 示例
- `MyProject_DiscoveryPRD_20240115.md` - 探索阶段PRD
- `MyProject_BusinessPRD_20240120.md` - 商业阶段PRD
- `MyProject_SystemicSolutionPRD_20240125.md` - 系统性方案PRD
- `MyProject_FeaturePRD_20240201.md` - 功能实现PRD
- `MyProject_TechnicalPRD_20240205.md` - 技术实现PRD
- `MyProject_SystemEvolutionPRD_20240210.md` - 系统演进PRD

### 其他文档命名格式
```
[项目名称]_[文档类型]_[日期].md
```

### 示例
- `MyProject_UserPersonas_20240118.md` - 用户画像
- `MyProject_TestPlan_20240203.md` - 测试计划
- `MyProject_API_20240206.md` - API文档

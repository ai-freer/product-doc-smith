## 概览
本文档说明如何将用户输入的内容智能映射到文档框架结构，并规范待补充项的标注和建议方式。

## 填充原则

### 1. 保持原有内容准确性
- 保留用户原文的核心观点和表述
- 不随意修改用户已有内容
- 仅进行格式调整和结构化处理

### 2. 内容映射优先级
- **完全匹配**:内容与文档框架章节直接对应 → 直接填充
- **部分匹配**:内容涵盖部分章节要点 → 填充并标注"部分"
- **间接关联**:内容与章节间接相关 → 智能关联并说明
- **无相关内容**:章节内容缺失 → 标注待补充

### 3. 智能扩展边界
- 基于已有内容进行合理推断
- 推断内容需有明确依据
- 超出推断范围的内容必须标注待补充

## 内容映射策略

### 1. 背景与目标章节
**映射要点**:
- 用户描述的"为什么做"、"为了解决什么问题" → 背景部分
- 用户描述的"达到什么效果"、"期望结果" → 目标部分
- 多个目标时需列出优先级

**示例**:
```
用户输入: "这个项目是为了解决用户反馈的登录问题，提升用户活跃度"
填充结果:
## 1. 背景与目标
- 背景:用户反馈存在登录问题，影响用户体验
- 目标:解决登录问题，提升用户活跃度
```

### 2. 核心内容/功能章节
**映射要点**:
- 具体功能点 → 功能描述
- 使用场景 → 用户场景
- 功能价值 → 用户价值/业务价值

**示例**:
```
用户输入: "新功能支持微信登录，用户可以不用记住密码"
填充结果:
## 2. 产品功能
- 核心功能:微信一键登录
- 用户场景:用户打开App时选择微信登录，无需输入密码
- 用户价值:简化登录流程，降低使用门槛
```

### 3. 技术方案章节
**映射要点**:
- 技术选型描述 → 技术选型
- 实现方式概述 → 整体架构
- 关键技术点 → 核心模块

**示例**:
```
用户输入: "使用Redis做缓存，提升接口响应速度"
填充结果:
## 2. 技术方案
- 技术选型:Redis缓存
- 整体架构:在应用层与数据库层之间增加Redis缓存层
- 核心模块:缓存读写模块、缓存更新策略
```

### 4. 风险与应对章节
**映射要点**:
- 可能的问题描述 → 风险识别
- 提到的解决方案 → 应对措施

**示例**:
```
用户输入: "可能会出现数据不一致，需要定时同步"
填充结果:
## 4. 技术风险
- 风险识别:缓存与数据库数据可能不一致
- 应对方案:实现定时同步机制，确保数据一致性
```

## 待补充项标注

### 1. 标注格式
**标准格式**: `[待补充]` 或 `[TODO]`

**位置规则**:
- 章节内容完全缺失 → 在章节标题后标注
  ```markdown
  ## 3. 实施方案 [待补充]
  ```

- 章节内容部分缺失 → 在具体缺失处标注
  ```markdown
  ### 2.2 用户场景
  已完成场景1...
  [待补充] 需要补充异常场景、边界场景
  ```

- 细节缺失 → 在段落中标注
  ```markdown
  核心功能已完成基础实现，[待补充] 需要补充性能指标和验收标准。
  ```

### 2. 标注分类
| 缺失类型 | 标注示例 | 说明 |
|---------|---------|------|
| 完全缺失 | `[待补充]` | 整个章节无内容 |
| 部分缺失 | `[待补充-部分]` | 有部分内容，但不够完整 |
| 细节缺失 | `[待补充-细节]` | 有框架但缺乏具体细节 |
| 数据缺失 | `[待补充-数据]` | 需要数据支撑的内容 |
| 验证缺失 | `[待补充-验证]` | 需要测试/验证的内容 |

## 补充建议规范

### 1. 建议格式
**标准格式**: `[待补充] 建议:具体说明`

**示例**:
```markdown
## 2.3 用户场景 [待补充]
建议:需要梳理以下场景:
1. 正常使用流程
2. 异常情况处理（网络失败、服务不可用）
3. 边界情况（超时、并发）
4. 用户权限校验场景
```

### 2. 建议内容要求
- **具体明确**:避免模糊表述，说明具体需要补充什么
- **可操作**:提供可执行的补充方向或问题清单
- **有层次**:按优先级或类别组织建议内容
- **关联性强**:建议内容应与当前章节高度相关

### 3. 常见补充建议文档框架

#### 业务场景补充建议
```markdown
[待补充] 建议:补充以下用户场景:
1. 目标用户在什么情况下会使用此功能？
2. 典型的使用流程是怎样的？
3. 有哪些异常场景需要考虑？
```

#### 技术方案补充建议
```markdown
[待补充] 建议:补充技术方案细节:
1. 具体的技术选型理由和对比分析
2. 核心模块的详细设计思路
3. 关键流程的流程图或伪代码
4. 接口定义和数据结构
```

#### 风险评估补充建议
```markdown
[待补充] 建议:补充风险评估:
1. 技术风险:稳定性、性能、兼容性
2. 业务风险:用户体验、数据安全
3. 项目风险:时间、资源、依赖
4. 每个风险的影响程度和发生概率
```

#### 数据支撑补充建议
```markdown
[待补充] 建议:补充数据支撑:
1. 目前的基线数据（现状指标）
2. 预期的改进幅度和量化目标
3. 数据来源和统计方式
4. 如何验证目标达成
```

### 4. 补充建议优先级
**高优先级**（必须补充）:
- 核心功能的完整描述
- 关键风险和应对措施
- 项目目标的成功标准

**中优先级**（建议补充）:
- 详细的使用场景
- 具体的实施细节
- 数据支撑和验证方案

**低优先级**（可选补充）:
- 扩展功能的描述
- 未来规划内容
- 辅助性说明材料

## 补充清单输出

### 1. 清单位置
在文档末尾添加"补充建议清单"章节

### 2. 清单格式
```markdown
## 附录:补充建议清单

### 必须补充（高优先级）
- [ ] 章节X:具体补充内容
- [ ] 章节Y:具体补充内容

### 建议补充（中优先级）
- [ ] 章节A:具体补充内容
- [ ] 章节B:具体补充内容

### 可选补充（低优先级）
- [ ] 章节C:具体补充内容
- [ ] 章节D:具体补充内容
```

### 3. 清单内容
- 汇总文档中所有标注的待补充项
- 按优先级排序
- 每项明确标注所属章节
- 提供补充的具体方向和要点

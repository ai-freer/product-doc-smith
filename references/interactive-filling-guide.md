## 概述

### 什么是交互式填充？

交互式填充是指当用户输入的内容不足时，智能体通过询问关键问题，引导用户逐步完善内容，最终生成完整文档的过程。根据内容充足度的不同，采用不同程度的互动方式。

### 适用场景

- ✅ 用户只有一个简单的想法或概念（完整引导）
- ✅ 用户输入的内容字数较少（少于100字）（完整引导）
- ✅ 用户内容缺乏结构化信息（完整引导）
- ✅ 用户内容部分缺失，需要补充关键章节（部分引导）
- ✅ 用户内容较充足，但需要确认核心要点（关键确认）
- ✅ 用户希望帮助梳理思路（完整引导）
- ✅ 用户不确定如何组织内容（完整引导）

### 不适用场景

- ❌ 用户已提供非常完整的文档草稿（直接填充）
- ❌ 用户输入内容包含详尽的结构化信息（直接填充）

## PRD阶段识别与文档框架选择

### 为什么要识别PRD阶段？

不同阶段的PRD有不同的**颗粒度**和**侧重点**：
- **探索阶段**：关注问题验证、商业价值，信息粗略、开放
- **方案阶段**：关注整体方案、系统边界，信息中等、结构化
- **实现阶段**：关注功能细节、技术实现，信息详细、精确
- **演进阶段**：关注长期规划、架构演进，信息宏观、战略性

识别PRD阶段有助于：
- ✅ 选择合适的文档框架（不同阶段对应不同颗粒度的文档结构）
- ✅ 调整填充策略（早期阶段更多引导，后期阶段更多填充）
- ✅ 生成恰当的内容（避免过早关注细节或过晚讨论战略）

### PRD阶段分类

#### 阶段1: 探索与判断（Discovery & Strategy）

**特点**：问题未明，需要验证
- **核心问题**：问题是否真实存在？是否值得做？
- **信息特征**：粗略、开放、假设性强
- **适用文档框架**：
  - `Default Product Requirements Document`（通用PRD）
  - `Business PRD-BRD`（商业价值分析）
  - `Discovery / Opportunity PRD`（探索性PRD）

**关键词识别**：
- 探索、验证、假设、痛点、机会、MVP
- 是否值得、要不要做、为什么现在
- 商业价值、成本效益、投资回报

**示例用户输入**：
- "想做一个会员系统，不知道是否可行"
- "用户留存低，想验证会员是否能解决"
- "考虑做社交功能，需要评估商业价值"

---

#### 阶段2: 方案成型（Solution Formation）

**特点**：问题明确，需要设计方案
- **核心问题**：如何解决问题？方案边界是什么？
- **信息特征**：中等、结构化、方案导向
- **适用文档框架**：
  - `Systemic Solution PRD template`（系统解决方案PRD）⭐推荐
  - `Technical Design Document`（技术设计文档）
  - `Experiment / Validation PRD`（验证方案PRD）

**关键词识别**：
- 方案、设计、架构、系统、解决方案
- 端到端、跨系统、协同关系、方案边界
- 功能模块、技术选型、系统设计

**示例用户输入**：
- "会员系统的整体方案设计"
- "设计一个实时聊天功能的完整方案"
- "订单系统重构的技术方案"

---

#### 阶段3: 交付与实现（Delivery & Execution）

**特点**：方案确定，需要指导实现
- **核心问题**：具体如何实现？功能细节是什么？
- **信息特征**：详细、精确、执行导向
- **适用文档框架**：
  - `PRD_一级功能名称_二级功能名称`（功能级PRD）⭐推荐
  - `Technical Design Document`（技术PRD）
  - `Release Plan`（执行计划）

**关键词识别**：
- 功能、特性、实现、开发、交付
- 用户路径、交互逻辑、功能边界
- 接口、数据、性能、开发排期

**示例用户输入**：
- "会员充值功能的详细设计"
- "会员等级升级的实现逻辑"
- "Q3版本会员功能开发计划"

---

#### 阶段4: 长期演进（Long-term Evolution）

**特点**：系统运行，需要规划演进
- **核心问题**：未来如何发展？长期规划是什么？
- **信息特征**：宏观、战略性、长期性
- **适用文档框架**：
  - `Default Product Requirements Document`（长期规划PRD）
  - `System Evolution PRD`（系统演进PRD）
  - `Go-to-Market Plan`（市场推广计划）

**关键词识别**：
- 演进、规划、长期、未来、路线图
- 架构演进、能力扩展、系统升级
- 战略方向、增长规划、长期目标

**示例用户输入**：
- "会员系统未来2年的演进规划"
- "从百万级到千万级用户的架构演进"
- "会员体系长期发展战略"

---

### PRD阶段识别决策树

```
第一步：判断是否为PRD
  IF 包含"PRD"、"产品需求"、"需求文档"等关键词 THEN
    继续第二步
  ELSE
    按常规流程处理
  END IF

第二步：判断PRD阶段
  IF 包含"探索"、"验证"、"假设"、"MVP"、"是否值得"、"商业价值" THEN
    → 阶段1: 探索与判断
  ELSE IF 包含"方案"、"设计"、"架构"、"系统"、"端到端"、"整体" THEN
    → 阶段2: 方案成型
  ELSE IF 包含"功能"、"实现"、"开发"、"交付"、"详细"、"接口" THEN
    → 阶段3: 交付与实现
  ELSE IF 包含"演进"、"规划"、"长期"、"未来"、"路线图"、"战略" THEN
    → 阶段4: 长期演进
  ELSE
    → 无法判断，询问用户
  END IF
```

### 交互式填充流程中的阶段判断

**在"步骤3: 识别内容类型"后增加"步骤3.5: 判断PRD阶段"**：

```
3. 识别内容类型
   ↓
3.5. 判断PRD阶段（仅PRD类文档）
   ├→ 阶段1: 探索与判断 → 选择粗粒度文档框架 + 完整引导
   ├→ 阶段2: 方案成型 → 选择中粒度文档框架 + 部分引导
   ├→ 阶段3: 交付与实现 → 选择细粒度文档框架 + 关键确认
   ├→ 阶段4: 长期演进 → 选择宏观文档框架 + 部分引导
   └→ 无法判断 → 询问用户当前阶段
   ↓
4. 选择合适文档框架
```

**示例对话**：

```
智能体：检测到这是一个产品需求文档。
        根据您的描述，我判断这处于"方案成型"阶段，
        建议使用《Systemic Solution PRD template》文档框架，
        这个文档框架适合描述端到端的系统解决方案。
        
        对吗？或者您当前处于其他阶段？
        
        - 探索与判断：问题验证、商业价值分析
        - 方案成型：整体方案设计、系统边界
        - 交付与实现：功能细节、技术实现
        - 长期演进：战略规划、架构演进

用户：对，是方案成型阶段。

智能体：好的，我将使用《Systemic Solution PRD template》，
        并针对方案成型的特点，重点引导您描述：
        1. 整体方案设计思路
        2. 系统边界和协同关系
        3. 关键功能和架构决策
```

---

### 阶段识别的注意事项

**避免过度精确**：
- 用户不需要精确到"Strategic PRD" vs "Business PRD-BRD"
- 只需要识别到4个大阶段即可
- 重点是为用户提供合适的文档框架选择

**允许用户覆盖**：
- 智能体给出阶段判断后，询问用户是否正确
- 用户可以手动选择其他阶段
- 以用户的选择为准

**灵活适配**：
- 有些PRD可能横跨多个阶段
- 优先选择最符合主要特征的阶段
- 或提供多个文档框架供用户选择

## 输入内容充足度判断

### 判断标准（4档）

| 档位 | 字数 | 信息点数量 | 结构化程度 | 互动程度 | 处理流程 |
|-----|------|-----------|-----------|---------|---------|
| **详尽** | >500字 | >5个 | 完整结构 | 几乎不互动 | 流程A: 直接填充 |
| **充足** | 300-500字 | 3-5个 | 结构化 | 关键确认 | 流程B: 关键确认式填充 |
| **一般** | 100-300字 | 1-2个 | 部分结构 | 部分引导 | 流程C: 部分交互式引导 |
| **不足** | <100字 | <2个 | 无结构 | 完整引导 | 流程D: 完整交互式引导 |

**字数判断**:
- 详尽: > 500字
- 充足: 300-500字
- 一般: 100-300字（需判断内容质量）
- 不足: < 100字

**信息点数量**:
- 详尽: 包含5个及以上关键信息点（背景、目标、范围、功能、技术选型、风险、计划等）
- 充足: 包含3-5个关键信息点（目标、范围、核心功能、技术选型等）
- 一般: 包含1-2个关键信息点
- 不足: 无明确信息点

**结构化程度**:
- 详尽: 有完整的章节结构和丰富的细节
- 充足: 有明确的章节结构或逻辑层次
- 一般: 有部分结构化信息
- 不足: 完全无结构

**示例对比**:

| 用户输入 | 判断结果 | 原因 | 使用流程 |
|---------|---------|------|---------|
| "做一个会员系统" | 不足 | 只有1个信息点，字数少，无结构 | 流程D: 完整交互式引导 |
| "开发一个会员系统，包含注册、充值、等级管理功能，目标是提升用户留存" | 一般 | 有3个信息点，但字数少 | 流程C: 部分交互式引导 |
| "产品名称：会员系统<br>功能：用户注册、充值管理、等级升级<br>目标：提升用户留存和付费转化<br>技术栈：Java + MySQL<br>预计时间：3个月" | 充足 | 信息点多，结构化程度高 | 流程B: 关键确认式填充 |
| "## 1. 项目背景<br>我们公司是电商平台，目前用户留存率只有20%，低于行业平均水平的35%。<br><br>## 2. 项目目标<br>通过建立会员体系，提升用户留存率至30%，付费转化率提升15%。<br><br>## 3. 核心功能<br>### 3.1 会员注册<br>支持微信、手机号两种注册方式，注册即送新人礼包。<br>### 3.2 充值管理<br>支持月卡、季卡、年卡三种充值方式，支持微信、支付宝支付。<br>### 3.3 等级升级<br>根据累计充值金额自动升级等级，等级越高享有的折扣越大。<br>...[约800字]" | 详尽 | 字数>500，信息点多，结构完整，细节丰富 | 流程A: 直接填充 |

### 判断流程

1. **初步评估**: 检查字数落在哪个档位
2. **信息点提取**: 识别关键信息点（背景、目标、范围、功能、技术等）
3. **结构化判断**: 检查是否有明确的章节或列表
4. **综合判断**: 结合以上因素做出最终判断

**决策逻辑**:
```
IF 字数 >= 500 AND 信息点 >= 5 AND 完整结构 THEN
    档位: 详尽 → 使用流程A: 直接填充
ELSE IF 字数 >= 300 AND 字数 < 500 AND 信息点 >= 3 AND 信息点 <= 5 AND 结构化 THEN
    档位: 充足 → 使用流程B: 关键确认式填充
ELSE IF 字数 >= 100 AND 字数 < 300 AND 信息点 >= 1 AND 信息点 <= 2 AND 部分结构 THEN
    档位: 一般 → 使用流程C: 部分交互式引导
ELSE IF 字数 < 100 OR 信息点 < 2 OR 无结构 THEN
    档位: 不足 → 使用流程D: 完整交互式引导
END IF
```

### 互动程度说明

**详尽档位**（流程A: 直接填充）:
- **互动程度**: 几乎不互动
- **处理方式**: 直接填充内容，输出文档
- **可选环节**: 询问用户是否需要快速验证核心要点
- **问题数量**: 0-1个（快速验证）

**充足档位**（流程B: 关键确认式填充）:
- **互动程度**: 关键确认
- **处理方式**: 填充内容后，用1-2个简洁问题确认核心要点
- **问题特点**: 高效、简洁，一次确认多个要点
- **问题数量**: 1-2个

**一般档位**（流程C: 部分交互式引导）:
- **互动程度**: 部分引导
- **处理方式**: 填充已有内容，对缺失的关键章节进行引导
- **问题特点**: 聚焦、高效，一次询问一个章节
- **问题数量**: 2-3个（针对关键章节）

**不足档位**（流程D: 完整交互式引导）:
- **互动程度**: 完整引导
- **处理方式**: 逐项询问所有核心章节
- **问题特点**: 开放、详细，从零开始构建文档
- **问题数量**: 5-8个（涵盖主要章节）

## 不同档位的处理流程

### 流程A: 直接填充（详尽档位）

**适用**: 字数>500，信息点>5，完整结构

```
1. 用户输入内容
   ↓
2. 检测为"详尽"档位
   ↓
3. 选择合适文档框架
   ↓
4. 智能填充内容
   ↓
5. 可选:快速验证（1个问题）
   ├→ 用户需要: 询问 "是否需要快速验证核心要点？"
   │              ├→ 是: 用1个问题快速确认
   │              └→ 否: 跳过
   └→ 用户不需要: 跳过
   ↓
6. 输出标准化文档
```

**示例话术**:
- "文档已生成，是否需要我快速验证核心要点？"
- "我理解您的目标是XXX，功能是XXX，对吗？"

### 流程B: 关键确认式填充（充足档位）

**适用**: 字数300-500，信息点3-5，结构化

```
1. 用户输入内容
   ↓
2. 检测为"充足"档位
   ↓
3. 选择合适文档框架
   ↓
4. 智能填充内容
   ↓
5. 关键确认环节（1-2个问题）
   - 快速确认背景、目标、核心功能
   - 使用简洁的确认问题，一次性确认多个要点
   - 示例: "我理解您的项目目标是XXX，核心功能是XXX，技术选型是XXX，对吗？"
   ↓
6. 根据确认结果调整内容
   ↓
7. 输出标准化文档
```

**示例话术**:
- "我先填充了您提供的内容，现在确认一下核心要点：您的目标是XXX，主要功能是XXX，技术选型是XXX，对吗？"

### 流程C: 部分交互式引导（一般档位）

**适用**: 字数100-300，信息点1-2，部分结构

```
1. 用户输入内容
   ↓
2. 检测为"一般"档位
   ↓
3. 选择合适文档框架
   ↓
4. 填充已有内容
   ↓
5. 识别缺失的关键章节
   ↓
6. 生成引导问题（2-3个）
   - 聚焦于缺失的关键章节
   - 一次询问一个章节
   - 问题要简洁高效
   ↓
7. 逐项询问并填充
   ↓
8. 其他已有章节直接填充
   ↓
9. 输出标准化文档
```

**示例话术**:
- "我已填充您提供的内容，现在需要补充几个关键章节。首先，项目的背景是什么？"
- "好的，那项目的核心目标是什么？"

### 流程D: 完整交互式引导（不足档位）

**适用**: 字数<100，信息点<2，无结构

```
1. 用户输入内容
   ↓
2. 检测内容充足度
   ├→ 足够 → 流程:直接填充
   └→ 不足 → 继续下一步
   ↓
3. 识别内容类型
   ↓
3.5. 判断PRD阶段（仅PRD类文档）
   ├→ 阶段1: 探索与判断 → 选择粗粒度文档框架 + 完整引导
   ├→ 阶段2: 方案成型 → 选择中粒度文档框架 + 部分引导
   ├→ 阶段3: 交付与实现 → 选择细粒度文档框架 + 关键确认
   ├→ 阶段4: 长期演进 → 选择宏观文档框架 + 部分引导
   └→ 无法判断 → 询问用户当前阶段
   ↓
4. 选择合适文档框架
   ↓
5. 告知用户使用文档框架和阶段判断
   ↓
6. 基于文档框架和阶段生成引导问题
   ↓
7. 逐项询问用户
   ↓
8. 用户回答问题
   ↓
9. 填充对应章节
   ↓
10. 是否还有重要章节未填充？
   ├→ 是 → 返回步骤6
   └→ 否 → 继续下一步
   ↓
11. 整理和完善文档
   ↓
12. 输出最终文档
   ↓
13. 询问是否继续完善（可选）
```

### 关键步骤说明

#### 步骤3: 识别内容类型

通过关键词匹配识别文档类型：

| 关键词 | 推荐文档框架 | PRD阶段 | 备注 |
|-------|---------|---------|------|
| **探索阶段 PRD** |
| 探索、发现、假设、验证、机会 | `Discovery PRD` | 探索 | 问题验证、用户研究 |
| 商业价值、ROI、市场机会 | `Business PRD-BRD` | 探索 | 商业价值分析 |
| **方案阶段 PRD** |
| 方案、设计、架构、系统、端到端、整体 | `Systemic Solution PRD template` | 方案 | 系统解决方案 ⭐ 推荐 |
| 实验、A/B测试、MVP、验证 | `Experiment PRD` | 方案 | 实验验证 |
| **实现阶段 PRD** |
| 功能、特性、功能模块、功能细节 | `Feature PRD` | 实现 | 功能级设计 |
| 技术实现、技术细节、技术PRD | `Technical PRD` | 实现 | 技术实现 |
| **演进阶段 PRD** |
| 演进、规划、长期、路线图、战略 | `System Evolution PRD` | 演进 | 长期演进规划 |
| **其他 PRD 相关** |
| PRD目录、结构、章节 | `PRD 文档目录结构` | - | 文档结构规划 |
| 一级功能、二级功能 | `PRD_一级功能名称_二级功能名称` | 实现 | 功能模块命名 |
| OKR、目标、关键结果 | `OKRs` | 方案/演进 | 目标管理 |
| Default PRD（通用） | `Default Product Requirements Document` | 探索/演进 | 通用PRD文档框架 |
| **技术设计类** |
| 技术、架构、设计、方案 | `Technical Design Document` | - | 技术方案文档 |
| API、接口、文档 | `API Documentation` | - | API接口文档 |
| **用户研究类** |
| 用户、画像、特征 | `User Personas` | - | 用户画像分析 |
| 旅程、路径、体验、触点 | `Customer Journey Map` | - | 用户旅程地图 |
| 用户测试、可用性测试 | `User Testing Plan` 或 `Usability Test Plan` | - | 用户测试计划 |
| **市场分析类** |
| 竞品、对比、分析 | `Competitive Analysis Report` | - | 竞品分析报告 |
| GTM、市场推广、上市 | `Go-to-Market Plan` | - | 市场推广计划 |
| 发布、版本、迭代 | `Release Plan` | - | 发布计划 |
| FAQ、问答、常见问题 | `PR FAQ` | - | 产品发布FAQ |
| **其他类** |
| 无障碍、合规、可访问性 | `Accessibility Compliance Checklist` | - | 无障碍合规检查 |

**无法识别时**: 询问用户具体想生成什么类型的文档。

**注意**：
- 如果多个关键词匹配，优先推荐最相关的文档框架
- PRD类文档需要进一步判断PRD阶段（见步骤3.5）
- 用户测试相关文档会区分 `User Testing Plan` 和 `Usability Test Plan`

#### 步骤5: 告知用户使用文档框架

示例话术:
```
"根据您的需求，我将使用《产品需求文档》文档框架来帮您完善内容。
这个文档框架包含以下章节:
1. 项目背景与目标
2. 产品功能
3. 非功能性需求
4. 用户体验
5. 数据与指标
6. 项目计划

我将逐项询问您关键问题，请您根据实际情况回答。
可以吗？"
```

#### 步骤7: 逐项询问用户

**原则**:
- 一次问一个问题或一组相关问题
- 问题要具体、开放、有引导性
- 优先询问核心章节
- 尊重用户节奏，不催促

#### 步骤10: 判断是否继续

**继续条件**:
- 还有2个及以上重要章节未填充
- 用户明确表示想继续完善
- 文档整体完整度低于60%

**结束条件**:
- 主要核心章节已填充（背景、目标、核心内容）
- 用户表示满意或不想继续
- 文档完整度达到80%以上

## 引导问题生成

### 问题设计原则

**1. 开放性**
- ✅ 请描述这个功能的用户场景是什么？
- ❌ 用户场景是A还是B？

**2. 具体化**
- ✅ 这个功能主要面向哪类用户群体？请描述用户画像。
- ❌ 用户是谁？

**3. 引导性**
- ✅ 这个功能的目标是什么？希望达到什么效果？
- ❌ 目标是什么？

**4. 可操作性**
- ✅ 您计划通过什么方式来实现这个功能？（如：自研、第三方服务等）
- ❌ 实现方式？

### 问题类型文档框架

#### 背景类问题
- 这个需求产生的背景是什么？
- 为什么需要做这个功能/项目？
- 目前存在什么问题或痛点？
- 这个需求主要解决什么问题？

#### 目标类问题
- 这个项目/功能的核心目标是什么？
- 希望达到什么效果？
- 成功的标准是什么？
- 预期的业务价值是什么？

#### 功能类问题
- 请描述这个功能的核心内容
- 主要包含哪些功能模块？
- 这些功能之间的关系是什么？
- 用户如何使用这个功能？

#### 场景类问题
- 请描述典型的使用场景
- 目标用户是谁？有什么特征？
- 用户在什么情况下会使用这个功能？
- 有哪些特殊场景需要考虑？

#### 技术类问题
- 计划使用什么技术栈？
- 为什么选择这些技术？
- 有哪些技术难点或风险？
- 如何解决这些技术问题？

#### 风险类问题
- 这个项目可能面临哪些风险？
- 如何应对这些风险？
- 有哪些依赖或限制条件？

### 问题优先级

**高优先级（必问）**:
- 项目背景
- 核心目标
- 主要功能/内容
- 目标用户/场景

**中优先级（建议问）**:
- 技术方案
- 实施计划
- 风险评估

**低优先级（可选问）**:
- 详细实施细节
- 后续规划
- 辅助性说明

### 专门文档类型的引导策略

#### 用户研究类文档（User Personas、Customer Journey Map、User Testing Plan）

**特点**: 深度用户洞察，需要大量用户数据和研究

**引导策略**:
1. **数据收集优先**: 先询问是否有现有用户数据、调研结果、访谈记录
2. **假设性引导**: 如果没有真实数据，引导用户描述假设性用户画像或场景
3. **多角度提问**: 从用户视角、产品视角、业务视角多维度提问
4. **场景化引导**: 使用具体场景和故事化描述，避免抽象问题

**示例对话（用户画像）**:
```
智能体：我了解到您需要创建用户画像文档。
        
        首先，请问您是否有现有的用户数据或调研结果？
        （如：用户访谈记录、问卷数据、行为分析等）

用户：没有，我们还没有做过用户调研。

智能体：没关系，我们可以基于假设和经验来构建用户画像。
        
        请先描述一下您的目标用户：
        - 他们的年龄范围大概是多少？
        - 主要是什么职业或身份？
        - 使用这个产品的目的是什么？

用户：主要是25-35岁的职场白领，日常通勤需要打车服务。

智能体：好的，这是一类重要的用户群体。
        
        接下来我想了解更多：
        - 他们通常在什么场景下打车？（如：上下班、出差、聚会）
        - 对打车服务最关心的是什么？（如：价格、速度、服务质量）
        - 有什么特别的痛点和需求？
```

**示例对话（用户旅程地图）**:
```
智能体：我了解到您需要创建用户旅程地图。
        
        请问这是针对哪个用户群体的旅程？
        （可以是特定的用户画像，也可以是通用用户）

用户：针对新注册用户。

智能体：好的，新用户旅程地图。
        
        请描述新用户从第一次接触产品到成为活跃用户的完整路径：
        1. 他们如何知道这个产品的？（触点）
        2. 他们是如何注册的？（渠道）
        3. 注册后做了什么？（行为）
        4. 遇到了哪些问题？（痛点）
        5. 什么时候决定留下来？（关键时刻）
```

#### 测试计划类文档（Usability Test Plan、User Testing Plan）

**特点**: 明确的测试目标和方法论，需要具体可执行的测试方案

**引导策略**:
1. **目标导向**: 先明确测试的核心目标和预期成果
2. **方法论引导**: 询问测试方法（访谈、可用性测试、A/B测试等）
3. **资源评估**: 询问可用资源（测试用户数量、时间、工具）
4. **场景细化**: 引导用户描述具体的测试场景和任务

**示例对话（可用性测试计划）**:
```
智能体：我了解到您需要制定可用性测试计划。
        
        首先请问：这次测试的主要目标是什么？
        （如：验证新功能是否易用、发现界面问题、评估用户体验等）

用户：想验证新设计的会员功能是否好用。

智能体：明白了，目标是验证会员功能的可用性。
        
        接下来请问：
        1. 您计划用什么测试方法？
           （如：实验室测试、远程测试、线上可用性测试）
        2. 需要多少测试用户参与？
        3. 测试的主要场景是什么？

用户：用远程测试，找10个用户，测试会员注册和充值两个场景。

智能体：好的，远程测试、10个用户、两个核心场景。
        
        那么测试的任务具体是什么？
        （请描述用户在测试中需要完成的具体操作）

用户：用户需要完成注册会员，并充值一个月会员。

智能体：了解。关于测试用户：
        1. 他们的特征是什么？（年龄、性别、产品使用经验）
        2. 如何招募这些测试用户？
```

#### API文档类（API Documentation）

**特点**: 技术性强，需要精确的接口定义和数据格式

**引导策略**:
1. **端点优先**: 先询问API的主要端点和功能
2. **请求格式**: 逐项确认请求方式、参数、认证
3. **响应格式**: 询问响应数据结构和示例
4. **错误处理**: 询问错误码和异常情况

**示例对话（API文档）**:
```
智能体：我了解到您需要编写API文档。
        
        请问这个API的主要功能是什么？
        （如：用户登录、获取订单列表、支付等）

用户：是一个用户登录的API。

智能体：好的，用户登录API。
        
        请确认以下信息：
        1. API的请求地址是什么？
        2. 使用什么HTTP方法？（GET、POST、PUT、DELETE）
        3. 请求参数有哪些？

用户：POST /api/login，参数是username和password。

智能体：了解。请求体格式是什么？
        （JSON、Form Data、XML等）

用户：JSON格式。

智能体：好的。认证方式是什么？
        （如：API Key、OAuth、Token）

用户：Token认证，登录成功后返回token。

智能体：了解。那登录成功后，响应数据包含哪些字段？
        请描述响应数据的JSON结构。
```

#### 市场推广类文档（Go-to-Market Plan、Release Plan、PR FAQ）

**特点**: 商业导向，强调时间节点、资源投入和效果衡量

**引导策略**:
1. **目标明确**: 先明确推广或发布的核心目标
2. **时间规划**: 询问关键时间节点和里程碑
3. **资源评估**: 询问预算、人力、渠道等资源
4. **效果衡量**: 询问KPI和成功标准

**示例对话（市场推广计划）**:
```
智能体：我了解到您需要制定市场推广计划。
        
        首先请问：这次推广的核心目标是什么？
        （如：提升品牌知名度、获取新用户、促进转化等）

用户：主要是获取新用户。

智能体：好的，获取新用户。
        
        接下来请问：
        1. 目标用户群体是谁？
        2. 预期的用户获取数量是多少？
        3. 推广的时间周期是多长？

用户：目标用户是年轻职场人，希望3个月内获取10万新用户。

智能体：了解。那么主要使用哪些推广渠道？
        （如：社交媒体、搜索引擎、内容营销、线下活动）

用户：主要用社交媒体和内容营销。

智能体：好的。预算大概是多少？
        以及如何衡量推广效果？（KPI指标）
```

#### 分析类文档（Competitive Analysis Report）

**特点**: 对比分析，需要明确的竞品对象和分析维度

**引导策略**:
1. **目标明确**: 先明确分析的目的和期望产出
2. **竞品识别**: 询问要分析的竞品列表
3. **维度选择**: 询问分析的维度（功能、价格、用户体验等）
4. **对比视角**: 引导用户从不同角度对比（优势、劣势、机会、威胁）

**示例对话（竞品分析报告）**:
```
智能体：我了解到您需要进行竞品分析。
        
        首先请问：这次分析的主要目的是什么？
        （如：了解市场格局、寻找差异化机会、学习竞争对手等）

用户：想看看竞品的会员功能，找出我们的差异化优势。

智能体：好的，目标是找差异化优势。
        
        接下来请问：
        1. 主要分析哪些竞品？
        2. 从哪些维度进行对比？

用户：主要分析A产品和B产品，对比功能、价格、用户体验。

智能体：了解。那我们逐个维度来分析：
        
        首先是功能维度，A产品和B产品的会员功能各有什么特点？
        （请描述它们的会员等级、特权、价格等）
```

## 各文档框架的关键问题

### 1. 产品需求文档 (Systemic Solution PRD template)

**必问问题**:
1. "请描述这个项目的背景，为什么需要做这个产品？"
2. "这个产品的核心目标是什么？希望达到什么效果？"
3. "主要包含哪些功能？请描述核心功能。"
4. "目标用户是谁？用户在什么场景下使用？"

**建议问题**:
5. "对性能有什么要求吗？（如：响应时间、并发数等）"
6. "有安全性方面的要求吗？"
7. "项目的预期时间计划是怎样的？"

### 2. 技术设计文档 (Technical Design Document)

**必问问题**:
1. "请描述这个技术项目的背景和需求。"
2. "计划使用什么技术栈？（编程语言、框架、数据库等）"
3. "为什么选择这些技术？有什么考虑？"
4. "请描述整体的架构设计思路。"

**建议问题**:
5. "有哪些核心模块？各自负责什么功能？"
6. "这个设计可能面临哪些技术挑战？如何应对？"
7. "对性能、可用性有什么要求？"

### 3. 竞品分析报告 (Competitive Analysis Report)

**必问问题**:
1. "请描述分析这个竞品的背景和目的。"
2. "主要分析哪些竞品？"
3. "从哪些维度进行对比？（如：功能、用户体验、价格等）"
4. "竞品的优势和劣势分别是什么？"

**建议问题**:
5. "我们的产品与竞品相比有哪些差异化优势？"
6. "有哪些可以借鉴的地方？"
7. "基于竞品分析，有什么改进建议？"

### 4. 用户画像 (User Personas)

**必问问题**:
1. "请描述目标用户的基本特征。（年龄、性别、职业等）"
2. "用户的典型使用场景是什么？"
3. "用户的核心需求是什么？"
4. "用户面临什么痛点或问题？"

**建议问题**:
5. "用户的使用习惯是怎样的？"
6. "用户对这个产品的期望是什么？"
7. "用户的决策因素是什么？（影响其使用的关键因素）"

### 5. 测试计划 (User Testing Plan)

**必问问题**:
1. "测试的目的是什么？"
2. "主要测试哪些功能或场景？"
3. "测试的目标用户是谁？如何招募？"

## 持续修改与完善

### 概述

当用户对已生成的文档提出修改意见时，智能体需要：
- ✅ 理解修改要求
- ✅ 检查修改是否涉及文档用途或阶段的变更
- ✅ 避免文档过度精细化导致不适合当前阶段
- ✅ 及时识别用户需求的阶段前进信号
- ✅ 获得用户确认后再推进

### 持续修改的关键原则

#### 1. 避免过度精细化

**核心原则**: 追问和修改补充应聚焦于**当前阶段的核心内容**，避免让文档过度变为明显不适合该阶段的颗粒度。

**示例对比**:
```
场景：用户在方案成型阶段（Systemic Solution PRD）的文档中，要求增加技术实现细节

❌ 错误做法：
智能体：好的，我添加详细的技术实现方案，包括数据库表结构、API接口定义、错误码列表...
问题：文档变得非常技术化，颗粒度过细，不适合方案成型阶段

✅ 正确做法：
智能体：我注意到您要求增加技术实现细节。当前文档使用Systemic Solution PRD文档框架（方案成型阶段），这个阶段的重点是整体方案设计和系统边界，而非技术实现细节。技术实现细节更适合Technical PRD或Feature PRD文档框架。

请问您希望：
- 选项A：保持在方案成型阶段，将技术细节标注为[待补充]
- 选项B：切换到Feature PRD或Technical PRD，适合技术实现阶段
```

**判断标准**:
- 如果修改要求涉及：
  - 详细的技术实现（代码、接口定义、数据结构）
  - 具体的功能交互逻辑
  - 详细的测试用例
  
  当前阶段为：探索/方案
  → 不适合，建议标注或切换文档框架

- 如果修改要求涉及：
  - 整体方案调整
  - 系统边界变更
  - 高层决策
  → 适合当前阶段

#### 2. 阶段一致性检查

**检查点**: 每次修改前，检查修改要求是否涉及文档用途或阶段的变更

**阶段对比表**:

| 当前阶段 | 修改内容倾向 | 是否适配 | 建议 |
|---------|------------|--------|------|
| 探索（Discovery/Business） | 具体功能实现 | ❌ 不适配 | 标注或切换 |
| 探索（Discovery/Business） | 技术架构细节 | ❌ 不适配 | 标注或切换 |
| 方案（Systemic/Experiment） | 技术实现细节 | ❌ 不适配 | 标注或切换 |
| 方案（Systemic/Experiment） | 详细用户故事 | ❌ 不适配 | 标注或切换 |
| 实现（Feature/Technical） | 整体战略规划 | ❌ 不适配 | 标注或切换 |
| 实现（Feature/Technical） | 宏观演进路线 | ❌ 不适配 | 标注或切换 |
| 演进（System Evolution） | 具体功能实现 | ❌ 不适配 | 标注或切换 |

**示例对话**:
```

#### 3. 识别阶段前进信号

**信号识别**: 持续的追问和修改可能表明用户需求在前进

**前进信号**:
```
从探索阶段 → 方案阶段：
  用户提问：从"这个问题真实存在吗？"
            → "具体的解决方案是什么？"
            → "系统的整体架构是怎样的？"

从方案阶段 → 实现阶段：
  用户提问：从"整体方案的思路是什么？"
            → "这个功能的具体实现逻辑是什么？"
            → "API接口的定义是什么？"

从实现阶段 → 演进阶段：
  用户提问：从"功能的实现细节是什么？"
            → "系统未来2-3年的演进规划是什么？"
            → "架构如何支持规模增长？"
```

**处理策略**:
1. **识别**: 检测到前进信号
2. **提醒**: 明确告知用户阶段前进
3. **确认**: 获得用户的正向确认
4. **推进**: 根据用户选择继续

**示例**:
```

         仅将技术细节标注为`[待补充]`？

1. 明确说明变更的影响和后果
2. 对比当前文档框架和目标文档框架的差异
3. 提供清晰的选项供用户选择
4. 获得用户的明确确认后，才执行修改或切换

### 修改与完善流程

#### 步骤1: 分析修改要求

1. **识别修改类型**
   - 修改内容是：增加 / 删除 / 调整
   - 涉及的章节和部分

2. **判断阶段一致性**
   - 修改内容是否适合当前PRD阶段
   - 是否会导致阶段偏移
   - 检查参考"阶段对比表"

3. **评估影响范围**
   - 对文档结构的影响
   - 对颗粒度的影响
   - 对侧重点的影响

#### 步骤2: 阶段检查与确认

如果修改涉及阶段偏移：

1. **提示用户**
   - 明确告知当前阶段定位
   - 说明修改的影响
   - 提供选项参考

2. **获得确认**
   - 用户确认保持在当前阶段
   - 或用户确认前进到新阶段

3. **根据确认执行**
   - 保持当前阶段：标注或引用
   - 前进到新阶段：切换文档框架

#### 步骤3: 执行修改

1. **直接应用修改**
   - 如果确认合适且不涉及阶段偏移
   - 直接应用修改内容
   - 保持文档结构完整

2. **标注或引用**
   - 对于超出当前颗粒度的内容
   - 标注为`[待补充]` 或 `详见XXX文档`
   - 在补充建议中说明适合的文档框架或文档

3. **生成更新文档**
   - 重新生成完整文档
   - 添加修改记录（如需要）

#### 步骤4: 文档记录管理

对于频繁修改的文档，可以添加修改记录章节：

```markdown
## 修改记录

| 日期 | 修改内容 | 影响章节 | 处理方式 |
|-----|---------|-----------|---------|
| 2024-01-15 | 增加用户画像章节 | 目标用户 | 简要引用 |
| 2024-01-18 | 添加数据库表结构 | 技术实现 | 标注待补充 |
```

## 最佳实践

### 1. 节奏控制

**好的做法**:
- 一次问1-2个相关问题
- 等待用户完整回答后再问下一个
- 给用户思考和回答的时间

**避免的做法**:
- 一次性问太多问题
- 催促用户快速回答
- 打断用户思路

### 2. 问题质量

**好的做法**:
- 问题具体、明确
- 提供示例或选项帮助用户理解
- 根据用户回答调整后续问题

**避免的做法**:
- 问题模糊、宽泛
- 问题过于专业或复杂
- 不考虑用户回答的上下文

### 3. 灵活调整

**好的做法**:
- 根据用户回答深度调整问题难度
- 用户回答简单时，追问细节
- 用户回答完整时，跳过相关问题

**避免的做法**:
- 机械地按固定顺序提问
- 不考虑用户的实际情况
- 强迫用户回答不想回答的问题

### 4. 阶段推进的决策

**好的做法**:
- 识别阶段前进信号后，及时提醒用户
- 提供清晰的选项，说明每个选项的影响
- 推荐创建新文档，保持各阶段文档独立
- 提醒用户保存当前阶段文档
- 明确说明文档之间的关系

**避免的做法**:
- 不提醒用户就自动切换阶段
- 在同一文档中混合多个阶段的内容
- 忽略文档保存的重要性
- 让用户混淆当前所处的阶段

### 5. 文档管理

**好的做法**:
- 推荐标准的文件命名规范
- 每个阶段文档独立保存
- 明确说明文档之间的关系和演进
- 保持文档结构的清晰和一致

**避免的做法**:
- 使用模糊的文件名
- 覆盖或丢失前一阶段的文档
- 文档关系不明确

### 6. 尊重用户选择

**好的做法**:
- 允许用户跳过某些问题
- 尊重用户说"不清楚"的回答
- 对跳过的内容标注为[待补充]

**避免的做法**:
- 强迫用户必须回答所有问题
- 批评用户的回答不够好
- 对跳过的内容进行价值评判

### 7. 文档输出

**好的做法**:
- 生成文档前告知用户
- 生成后询问是否需要继续完善
- 对不完整的内容明确标注

**避免的做法**:
- 直接生成文档不告知
- 不给用户修改和完善的机会
- 隐瞒不完整的内容
